# UAES-P02-ACCEPTANCE-BASELINE — Product Engineering 验收基准

| Field | Value |
|---|---|
| Acceptance ID | UAES-P02-ACCEPTANCE-BASELINE |
| Version | 1.0.0 |
| Status | DRAFT |
| Gate | UAES-02-GATE-001 |

## A. 需求完整性

- 每个需求具有唯一 ID。
- 需求来源可追踪。
- 目标、范围、非目标和约束明确。
- 用户角色和用户价值明确。
- 优先级和风险等级明确。
- 依赖和阻塞项明确。
- 未确认信息被显式标记。

## B. 业务规则与流程

- 业务规则独立编号。
- 每条关键规则有来源和责任人。
- 主流程、异常流程和边界条件完整。
- 状态机定义合法状态和转换。
- 并发、重试、超时和幂等要求已评估。
- 业务规则冲突有处理记录。

## C. 验收标准

- 验收条件可观察。
- 验收条件可重复执行。
- 验收结果有明确判定规则。
- 正常路径和异常路径均有覆盖。
- 非功能需求有对应验证方式。
- 产品验收与工程测试结果分离。

## D. 变更影响

- 业务影响已分析。
- 架构和模块边界影响已分析。
- 数据结构和迁移影响已分析。
- API 和第三方接口影响已分析。
- 体验和设计影响已分析。
- 安全与隐私影响已分析。
- 测试和回归影响已分析。
- 跨平台兼容性影响已分析。
- 发布、回滚和运营影响已分析。

## E. 需求追踪

- 需求关联设计文档。
- 需求关联实现模块或代码变更。
- 需求关联测试用例。
- 需求关联测试结果。
- 需求关联验收证据。
- 被删除或废弃的需求保留历史关系。

## F. 负面测试

- 缺少来源的需求不能通过 Gate。
- 重复需求 ID 不能通过 Gate。
- 未确认业务假设不能被伪装为已批准规则。
- 无验收标准的需求不能进入实施。
- 非法状态转换被拒绝。
- 缺少高风险影响分析时 Gate 必须阻断。
- 需求批准不能自动授予 AI 工程权限。
- IMPLEMENTED 不能自动变成 ACCEPTED。
- 缺少测试证据不能被标记为验证通过。

## G. Uter 领域专项测试

- 支付成功、失败、关闭、退款和异常状态有定义。
- 支付回调重复投递不会造成重复入账。
- 金额、币种、订单归属和渠道订单号有校验规则。
- 支付结果无法确认时存在主动查询和对账流程。
- uter.cc 支付域名与 uter.ai 运营站之间的业务责任边界明确。
- 余额入账有明确的唯一业务依据和幂等键。

## H. 最终验收状态

只有在所有适用项完成、阻断问题关闭、证据可追踪后，才能将 P02 Gate 结果标记为 PASS。

**文档交付本身不构成 P02 工程验收通过。**
