# UAES-02 — PRODUCT ENGINEERING STANDARD

**Document ID:** UAES-02-001  
**Standard:** UTER AI Engineering Standard  
**Domain:** Product Engineering  
**Version:** 1.0.0  
**Status:** DRAFT  
**Classification:** Enterprise Engineering Standard

---

# 1. 目的

本标准定义 Uter 项目的产品工程体系，规范从产品需求输入到最终软件交付的完整过程。

产品工程不是简单地将用户提出的需求转换为代码。

它必须经过：

需求理解 → 需求分析 → 业务规则定义 → 用户流程设计 → 状态建模 → 技术影响分析 → 验收标准制定 → 工程任务拆解 → 实现 → 验收。

AI 必须能够区分：

- 用户真正提出的要求。
- 用户已经确认的业务规则。
- 从现有系统中验证的事实。
- AI 自己提出的建议。
- 尚未确认的业务假设。

未经确认的假设不得被当作正式业务需求。

# 2. 产品工程基本原则

## UAES-02-001：需求完整性

每项正式需求 MUST 具有明确的目标、范围和验收条件。

## UAES-02-002：需求可追踪

每项正式需求 MUST 拥有唯一 Requirement ID。

## UAES-02-003：业务规则独立管理

业务规则 MUST 与具体代码实现分离。

## UAES-02-004：需求与实现分离

需求文档描述系统应该实现什么，不应直接绑定某种具体技术实现，除非技术限制本身属于需求约束。

## UAES-02-005：禁止擅自补充业务规则

AI MUST NOT 将推测、行业惯例或个人建议直接转化为已批准的业务规则。

## UAES-02-006：验收条件先于实现

所有具有明确业务结果的功能任务 MUST 在实现前定义可验证的验收条件。

## UAES-02-007：状态流转必须完整

涉及订单、支付、用户账户、任务、订阅、审核等状态的功能 MUST 定义合法状态、状态转换和异常处理。

## UAES-02-008：需求变更必须进行影响分析

修改已批准需求时 MUST 分析对业务、架构、数据、接口、安全、测试和文档的影响。

## UAES-02-009：需求冲突必须显式处理

当用户的新要求与已有业务规则冲突时，AI MUST 识别冲突，不得静默覆盖。

## UAES-02-010：交付必须具有验收证据

每项完成的需求 MUST 能够追踪到实现和验证结果。

# 3. 需求分类

所有需求必须归入以下类别之一。

| 类别 | ID 前缀 | 说明 |
|---|---|---|
| 功能需求 | FR | 系统必须提供的功能 |
| 非功能需求 | NFR | 性能、安全、可靠性等要求 |
| 业务需求 | BRQ | 企业或业务目标 |
| 用户体验需求 | UX | 用户交互和体验要求 |
| 技术约束 | TR | 技术、架构和平台限制 |
| 安全需求 | SR | 安全和隐私要求 |
| 兼容性需求 | CR | 浏览器、设备和平台兼容要求 |
| 合规需求 | CPR | 法律、监管和组织合规要求 |

一个功能可以同时关联多个需求类别，但必须有明确的主需求和关联关系。

# 4. 需求优先级

采用四级优先级：

| 等级 | 定义 | 处理原则 |
|---|---|---|
| P0 | 阻断级 | 必须优先解决 |
| P1 | 高优先级 | 当前交付周期必须完成 |
| P2 | 普通优先级 | 按计划实现 |
| P3 | 低优先级 | 可排期或延后 |

优先级不得替代风险等级。

一个 P3 功能如果涉及 R3 安全风险，仍必须遵循高风险安全要求。

# 5. 需求生命周期

正式需求采用以下状态：

- INTAKE
- ANALYZING
- CLARIFICATION_REQUIRED
- PROPOSED
- APPROVED
- PLANNED
- IN_PROGRESS
- IMPLEMENTED
- VERIFYING
- ACCEPTED
- REJECTED
- DEFERRED
- DEPRECATED

状态定义：

| 状态 | 定义 |
|---|---|
| INTAKE | 已收到需求 |
| ANALYZING | 正在分析 |
| CLARIFICATION_REQUIRED | 缺少关键业务信息 |
| PROPOSED | 已形成方案，等待批准 |
| APPROVED | 已批准 |
| PLANNED | 已进入实施计划 |
| IN_PROGRESS | 正在开发 |
| IMPLEMENTED | 已完成初步实现 |
| VERIFYING | 正在验证 |
| ACCEPTED | 验收通过 |
| REJECTED | 已拒绝 |
| DEFERRED | 延后处理 |
| DEPRECATED | 已废弃 |

不得将 IMPLEMENTED 等同于 ACCEPTED。

# 6. 需求输入

AI 接收需求后必须识别：

1. 用户目标。
2. 目标用户。
3. 使用场景。
4. 当前问题。
5. 期望行为。
6. 涉及模块。
7. 业务规则。
8. 数据影响。
9. 权限影响。
10. 安全影响。
11. 平台影响。
12. 验收条件。

缺失信息应区分：

- BLOCKING：缺失后无法安全或正确实施。
- NON_BLOCKING：可以在明确假设下继续。
- OPTIONAL：不影响核心功能。

对于 BLOCKING 信息，必须提出必要澄清。

# 7. 需求分析

需求分析必须覆盖：

## 7.1 业务分析

- 业务目标。
- 用户价值。
- 业务参与方。
- 业务前置条件。
- 正常流程。
- 异常流程。
- 业务边界。
- 业务限制。
- 成功条件。

## 7.2 用户分析

- 用户角色。
- 用户权限。
- 用户状态。
- 用户操作。
- 用户可见结果。
- 用户失败体验。

## 7.3 工程分析

- 现有模块。
- 相关接口。
- 数据结构。
- 依赖服务。
- 缓存影响。
- 并发影响。
- 跨平台影响。
- 测试影响。

## 7.4 风险分析

- 数据丢失。
- 重复提交。
- 重复扣款。
- 重复到账。
- 越权访问。
- 竞态条件。
- 服务中断。
- 外部服务异常。
- 回滚困难。

风险分析必须根据需求实际情况进行，不能仅复制通用清单。

# 8. 需求审批

以下需求原则上必须经过用户或授权负责人批准：

- 新增核心业务规则。
- 修改支付和退款规则。
- 修改用户权限。
- 修改账户余额规则。
- 修改数据保留政策。
- 修改用户隐私政策。
- 修改跨平台产品行为。
- 修改收费模式。
- 修改关键业务状态机。
- 引入高风险外部服务。

低风险、边界清楚的实现细节，可以由 AI 在已有授权内自行处理。

# 9. 需求拆分

需求拆分必须形成：

- Epic。
- Feature。
- User Story。
- Engineering Task。
- Test Case。

拆分原则：

1. 每个任务必须具有明确目标。
2. 每个任务必须具有可验证结果。
3. 任务之间必须明确依赖。
4. 不得将多个独立业务目标塞进一个任务。
5. 不得为了形式化拆分出大量无实际价值的任务。
6. 任务规模必须适合独立实现和验证。

# 10. 需求质量检查

正式需求必须满足：

- 清晰。
- 完整。
- 一致。
- 可测试。
- 可追踪。
- 可实现。
- 可验收。
- 风险明确。

不满足时不得直接进入正式实施状态。

# 11. 产品工程交付物

每项重要功能至少形成：

1. Requirement Record。
2. Business Rules。
3. User Flow。
4. Acceptance Criteria。
5. Technical Impact Analysis。
6. Engineering Tasks。
7. Test Mapping。
8. Verification Evidence。

简单缺陷修复可使用精简记录，但必须保留任务目标、影响范围和验证证据。

# 12. 强制规则

| Rule ID | 规则 | 级别 |
|---|---|---|
| UAES-02-001 | 需求必须明确目标和范围 | MUST |
| UAES-02-002 | 需求必须唯一编号 | MUST |
| UAES-02-003 | 业务规则独立管理 | MUST |
| UAES-02-004 | 需求与技术实现分离 | MUST |
| UAES-02-005 | 不得擅自补充业务规则 | MUST NOT |
| UAES-02-006 | 实现前定义验收条件 | MUST |
| UAES-02-007 | 关键状态流转必须建模 | MUST |
| UAES-02-008 | 需求变更必须影响分析 | MUST |
| UAES-02-009 | 需求冲突必须显式处理 | MUST |
| UAES-02-010 | 完成必须有验收证据 | MUST |

# 13. 验收标准

本标准通过验收必须证明：

1. 需求分类完整。
2. 需求状态完整。
3. 需求 ID 唯一。
4. 需求输入可以结构化。
5. 需求质量可以检查。
6. 业务规则可以独立管理。
7. 验收条件可以映射到测试。
8. 需求变更具有影响分析。
9. 需求冲突具有升级机制。
10. 完成状态具有可追溯证据。
